# Многопользовательский счётчик очков — дизайн

**Дата:** 2026-07-30
**Статус:** утверждён к реализации

---

## 1. Задача

Сейчас `score-counter` — офлайн-SPA на одном устройстве: состояние живёт в `localStorage`, экраны переключаются через `v-if` в `App.vue`.

Нужно публичное приложение, в котором компания друзей играет так:

1. Один создаёт комнату — с паролем или без.
2. Остальные находят её в лобби или открывают ссылку-приглашение и вводят пароль.
3. Хост жмёт «Старт», состав фиксируется, играют до выбранного количества очков.
4. В каждой раздаче игрок со своего телефона дописывает себе заработанные очки; изменения видят все.
5. Кто набрал лимит — победил. Игру можно перезапустить тем же составом.
6. У каждого игрока копится история: с кем играл, общий результат и раскладка по раздачам.

## 2. Принятые решения

| Решение | Выбор |
|---|---|
| Бэкенд | Свой Fastify-сервер + SQLite (`better-sqlite3`) |
| Хранилище | Один файл `/data/score.db` на томе Coolify |
| Хостинг | Тот же VPS (Timeweb, Coolify), отдельный контейнер, поддомен `score.fastio.ru` |
| Статика | Раздаётся тем же Fastify — один домен, нет CORS |
| Транспорт | REST на запись + SSE на чтение |
| Идентификация | Гость по нику, с возможностью привязать email и сохранить историю |
| Права на счёт | Каждый пишет только себе; хост может исправить чужой |
| Раздачи | Свободный ввод очков, без синхронных раундов |
| Исправления | Отмена записи (своей — любым, чужой — хостом), без удаления из журнала |
| Дозаход | Состав фиксируется на старте; вернуться можно только на своё место |
| Уход хоста | Автопередача роли через 60 секунд отсутствия |
| Плохая связь | Автопереподключение SSE; офлайн-очереди записей нет |
| PWA | Базовая: манифест, иконки, установка на главный экран |

### Что сознательно не делается

- **Офлайн-режим на одном устройстве.** Требует второй ветки логики счёта и правил слияния с сервером — заметный объём ради сценария, которого в задаче нет.
- **Зрители.** Комнату видит только участник.
- **Строгие раунды** с ожиданием ввода от всех.

### Изоляция от `fastio`

Приложение делит с `fastio` только физические ресурсы VPS (4 vCPU / 8 GB / 80 GB) и Traefik. Своя база, свой контейнер, свой том, свои миграции; Postgres и GoTrue из `fastio` не задействованы. Контейнеру выставляются лимиты 256 MB RAM / 0.5 CPU, чтобы сбой в счётчике не задел соседа.

## 3. Архитектура

Один Docker-контейнер, один процесс Node: Fastify отдаёт статику фронта, API и поток SSE.

```
score-counter/
├── client/            — Vue 3 SPA (переезжает из src/)
├── server/
│   └── src/
│       ├── domain/    — чистая логика: счёт, победитель, права, применение событий
│       ├── db/        — схема, миграции, запросы
│       ├── routes/    — auth, rooms, games, entries, events, history
│       └── realtime/  — реестр SSE-подписчиков, рассылка, presence
├── shared/            — типы, общие для клиента и сервера
└── Dockerfile
```

**Границы модулей.** `domain/` не знает ни про HTTP, ни про SQLite: это чистые функции над данными — посчитать счёт по журналу, определить победителя, ответить «может ли этот игрок отменить эту запись». Туда уходит логика, которую нужно покрыть тестами, и тестируется она без сервера и без базы. `realtime/` знает только, кому разослать событие, и ничего не знает об игре. `routes/` связывает их и валидирует вход.

**Текущий счёт не кэшируется в памяти.** Он всегда считается запросом к SQLite. Кэш комнат в памяти дал бы рассинхрон с базой и потерю состояния при рестарте контейнера, а выигрыш на таких объёмах неизмерим — файл целиком лежит в кэше ОС. В памяти живёт только реестр открытых SSE-соединений, который и так привязан к процессу.

SQLite работает в режиме WAL.

## 4. Модель данных

Иерархия: **комната** живёт долго и переживает несколько игр → **игра** — один заход до лимита очков (рестарт = новая игра) → **запись** — очки, дописанные игроком.

```sql
users          id, nickname, email?, password_hash?, created_at
sessions       token_hash, user_id, created_at, last_seen_at

rooms          id, code, name, password_hash?, host_user_id, created_at, closed_at?
room_members   room_id, user_id, joined_at, left_at?

games          id, room_id, score_limit, status, started_at, finished_at?, winner_user_id?
game_players   game_id, user_id, seat

score_entries  seq, id, game_id, user_id, points, created_by,
               created_at, voided_at?, voided_by?

room_events    seq, room_id, type, payload, created_at
```

У `score_entries` два ключа с разными задачами: `seq` — автоинкремент, задающий бесспорный порядок записей внутри игры; `id` — уникальный идентификатор, который генерирует клиент ради идемпотентности. Порядок нужен для правила «кто первым перешёл лимит», и брать его из `room_events` значило бы завязать подсчёт очков на транспортный журнал.

`games.status` ∈ `active | finished | abandoned`.

**Отмена не удаляет.** Счёт игрока — это `SUM(points) WHERE voided_at IS NULL`, а отменённая запись остаётся видна в списке раздач: всем понятно, что произошло, и спор «у меня было больше» не возникает. `created_by` отдельно от `user_id` показывает, когда хост исправил чужой счёт.

**Зачем две таблицы журнала.** `score_entries` — предметная: по ней считается счёт и строится история, с индексами под `SUM` и `GROUP BY`. `room_events` — транспортная: сквозной поток всего, что произошло в комнате, включая события без очков. `seq` — сквозной автоинкремент по таблице; при переподключении браузер присылает `Last-Event-ID`, сервер отдаёт `WHERE room_id = ? AND seq > ?`. Одной таблицей не обойтись: пришлось бы либо считать счёт разбором JSON, либо потерять события, не связанные с очками.

**История строится запросами, отдельного хранилища не нужно.** «Мои игры» — `games` через `game_players`; «с кем играл» — соперники по тем же `game_players`; «общий результат» — доля побед и средний счёт; «по раздачам» — `score_entries` игры в хронологии. Фиксация состава на старте здесь принципиальна: без неё «средний результат в игре на четверых» ничего не значит.

**Хранение.** Игры не удаляются — объём за годы измеряется мегабайтами. Комнаты без активности 30 дней помечаются `closed_at`.

**Ограничения полей.**

| Поле | Правило |
|---|---|
| `rooms.code` | 6 символов, верхний регистр, алфавит без похожих знаков (без `0`, `O`, `1`, `I`) |
| `rooms.name` | 1–40 символов |
| `users.nickname` | 1–20 символов, уникальность не требуется — игроки различаются по `id` |
| `games.score_limit` | 1–10000 |
| Число игроков в игре | 2–10 |
| `score_entries.points` | −10000…10000, ноль запрещён |

## 5. API

Сессия — случайный токен (32 байта) в `localStorage`, в базе хранится только его хэш, передаётся заголовком `Authorization: Bearer`. Cookie не используются: домен один, а токен переживает перезапуск браузера без настройки `SameSite`.

```
POST /api/auth/guest        {nickname}          → {token, user}
POST /api/auth/upgrade      {email, password}   → привязать email к текущему гостю
POST /api/auth/login        {email, password}   → {token, user}
GET  /api/me

GET  /api/rooms                                 → лобби: имя, есть ли пароль, число игроков, идёт ли игра
POST /api/rooms             {name, password?}
POST /api/rooms/:id/join    {password?}
POST /api/rooms/:id/leave

POST /api/rooms/:id/games   {scoreLimit}        → старт; он же рестарт тем же составом
POST /api/games/:id/entries {id, userId, points}
POST /api/entries/:id/void

GET  /api/rooms/:id/events                      → SSE

GET  /api/me/games                              → список моих игр
GET  /api/me/stats                              → сводка: игр, побед, частые соперники
GET  /api/games/:id                             → детали игры с раздачами
```

**Идемпотентность записи очков.** `id` в теле `POST /api/games/:id/entries` генерирует клиент. Повторный запрос с тем же `id` не создаёт вторую запись, а возвращает существующую. Это снимает двойной тап по кнопке и повтор запроса, оборвавшегося в момент отправки.

**Состав игры.** `POST /api/rooms/:id/games` берёт состав из текущих участников комнаты (`room_members` с `left_at IS NULL`) на момент нажатия «Старт» и копирует его в `game_players`. Рестарт работает точно так же — отдельной ветки логики для него нет. Если между играми никто не ушёл и не пришёл, состав тот же; если состав изменился, новая игра честно отражает это, а прошлая остаётся в истории нетронутой.

**Выход во время игры.** `POST /api/rooms/:id/leave` во время активной игры не убирает игрока из `game_players` — его очки остаются в счёте, а сам он может вернуться на своё место. Влияет только на то, попадёт ли он в состав следующей игры.

**Права.** Добавлять и отменять очки себе может любой участник игры; чужие — только хост. Стартовать и перезапускать игру — только хост. Проверки живут в `domain/` и вызываются из маршрутов.

**Лобби.** `GET /api/rooms` доступен любому авторизованному, включая гостя, и отдаёт только открытые комнаты. Содержимое комнаты — состав, счёт, журнал — видно исключительно её участникам.

**Пароль комнаты** хранится как хэш argon2id. На `join` — ограничение частоты попыток по IP и по комнате.

## 6. Протокол событий

Типы: `member_joined`, `member_left`, `host_changed`, `presence`, `game_started`, `game_finished`, `entry_added`, `entry_voided`.

Клиент загружает полное состояние комнаты при входе, дальше применяет события инкрементально. Каждое событие уходит в SSE с полем `id`, равным `seq`.

**Технические требования к SSE.** Heartbeat-комментарий раз в 25 секунд, иначе промежуточные прокси рвут простаивающее соединение. Заголовки `Cache-Control: no-cache` и `X-Accel-Buffering: no`, чтобы ответ не копился в буфере.

**Presence и автопередача хоста.** Сервер знает открытые SSE-соединения каждой комнаты. Если у хоста нет соединения 60 секунд, роль переходит к следующему онлайн-участнику и рассылается `host_changed`. Вернувшийся хост становится обычным игроком.

## 7. Клиент

Добавляется `vue-router` — сейчас экраны переключаются через `v-if` в `App.vue`.

| Маршрут | Содержимое |
|---|---|
| `/` | Лобби: список комнат, «Создать», свой ник |
| `/room/:code` | До старта — состав и «Старт» у хоста; после — табло |
| `/history` | Мои игры и сводка |
| `/history/:gameId` | Раздачи конкретной игры |

Ссылка-приглашение — это `/room/:code`: друг открывает её, вводит пароль и попадает внутрь, минуя поиск в лобби. Список в лобби остаётся вторым способом.

**Где выбирается лимит очков.** При создании комнаты задаются только имя и пароль — комната переживает несколько игр, а лимит принадлежит игре. Хост выбирает его в момент «Старта»; последнее значение подставляется по умолчанию, так что рестарт тем же лимитом — это одно нажатие.

**Переиспользование существующих компонентов.** `GameScreen.vue` остаётся табло, но счёт берёт из стора вместо локального состояния. `PlayerCard.vue` получает индикаторы «онлайн» и «это ты». `VictoryScreen.vue` получает кнопку «Играть ещё», создающую новую игру тем же составом. `SetupScreen.vue` распадается на две формы: создание комнаты и выбор лимита при старте.

Состояние — Pinia; стор комнаты применяет события из SSE. Тёмная тема и её сохранение в `localStorage` переносятся как есть.

**PWA:** `manifest.json`, иконки, поддержка установки на главный экран. Service worker кэширует только статические ассеты — данные всегда идут с сервера.

## 8. Краевые случаи

| Ситуация | Поведение |
|---|---|
| Обрыв связи | Баннер «нет связи», кнопки ввода заблокированы, SSE переподключается автоматически и догружает пропущенное по `Last-Event-ID` |
| Двойной тап | Идемпотентность по клиентскому `id` записи |
| Двое перешли лимит почти одновременно | Побеждает запись с меньшим `seq`; определяется в одной транзакции на сервере |
| Неверный пароль | 403 + ограничение частоты попыток |
| Комната закрыта или не найдена | Редирект в лобби с сообщением |
| Хост не вернулся | Автопередача роли через 60 секунд |
| Из идущей игры ушли все | Через сутки статус `abandoned`; в статистику побед не попадает |
| Гость чистит браузер | История теряется — показывается предложение привязать email |
| Рестарт контейнера | Состояние восстанавливается из SQLite; клиенты переподключают SSE |

## 9. Тестирование

Тесты ложатся на границы модулей из раздела 3.

- **`domain/`, Vitest.** Основная масса: счёт с отменами, определение победителя, права на отмену чужой записи, применение событий к состоянию. Без сервера и без базы.
- **Маршруты, `fastify.inject()` на временной SQLite.** Пароли комнат, идемпотентность записи очков, отказы по правам, фиксация состава на старте.
- **Интеграционный тест SSE.** Два подписчика: один пишет очки — второй получает событие; затем обрывается и догружает пропущенное по `Last-Event-ID`.

Реализация идёт по TDD: тест до кода.

## 10. Деплой

Многоступенчатый `Dockerfile`: сборка клиента через Vite, сборка сервера, финальный образ с Node 22 и собранной статикой. Том Coolify монтируется в `/data`. Переменные окружения: `PORT` и `DB_PATH`. Секрета для сессий не требуется: токен — это случайные 32 байта, в базе лежит его SHA-256, подписывать нечего. Traefik проксирует `score.fastio.ru` на контейнер, сертификат — из существующего wildcard `*.fastio.ru`. Бэкап — копирование `score.db` (через `sqlite3 .backup`, чтобы не поймать частичную запись).
