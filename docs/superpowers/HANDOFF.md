# Контекст проекта score-counter

Документ для входа в работу с нуля. Обновлять при завершении каждого плана.

**Состояние на 2026-07-30:** сервер готов и покрыт тестами, клиент не начат.

---

## Что строим

Публичный многопользовательский счётчик очков для настольных игр. Сценарий: один создаёт комнату (с паролем или без), друзья находят её в лобби или открывают ссылку-приглашение, хост жмёт «Старт», дальше каждый со своего телефона дописывает себе заработанные очки после раздачи, изменения видят все. Кто набрал лимит — победил, игру можно перезапустить тем же составом. У каждого игрока копится история: с кем играл, общий результат и раскладка по раздачам.

Исходно это была офлайн-SPA на одном устройстве с состоянием в `localStorage`.

---

## Принятые решения

| Решение | Выбор | Почему |
|---|---|---|
| Бэкенд | Свой Fastify + SQLite одним процессом | Файл на диске с транзакциями; масштаба хватает с запасом |
| Хранилище | `/data/score.db`, режим WAL | Бэкап — копия файла |
| Хостинг | Тот же VPS, что и `fastio` (Timeweb, Coolify), поддомен `score.fastio.ru` | Wildcard-сертификат уже есть; изоляция контейнером и лимитами 256 MB / 0.5 CPU |
| Статика | Раздаётся тем же Fastify | Один домен — нет CORS, один деплой |
| Транспорт realtime | REST на запись + SSE на чтение | Браузер сам переподключается и догружает пропущенное по `Last-Event-ID` |
| Идентификация | Гость по нику, потом можно привязать email | Низкий порог входа, история сохраняется |
| Права на счёт | Каждый пишет только себе, хост может исправить чужой | Соответствует сценарию «каждый со своего телефона» |
| Раздачи | Свободный ввод очков, без синхронных раундов | Не нужно ждать всех |
| Исправления | Отмена записи без удаления из журнала | Отменённая запись видна всем — споров не возникает |
| Дозаход | Состав фиксируется на «Старте»; вернуться можно на своё место | Честная статистика |
| Уход хоста | Автопередача роли через 60 секунд | Игра не застревает |
| Плохая связь | Только автопереподключение SSE, офлайн-очереди нет | Сознательно отброшено как дорогое |
| PWA | Базовая: манифест, иконки, установка | Дёшево, ощущается как приложение |
| Node | 22 (`.nvmrc`), pnpm 9.15.0 | Готовые бинарники для `better-sqlite3` и `@node-rs/argon2` |

**Сознательно не делается:** офлайн-режим на одном устройстве, зрители, строгие раунды с ожиданием всех.

## Модель данных

Иерархия: **комната** живёт долго и переживает несколько игр → **игра** — один заход до лимита (рестарт = новая игра) → **запись** — очки, дописанные игроком.

```sql
users          id, nickname, email?, password_hash?, created_at
sessions       token_hash, user_id, created_at, last_seen_at
rooms          id, code, name, password_hash?, host_user_id, created_at, closed_at?
room_members   room_id, user_id, joined_at, left_at?
games          id, room_id, score_limit, status, started_at, finished_at?, winner_user_id?
game_players   game_id, user_id, seat
score_entries  seq, id, game_id, user_id, points, created_by, created_at, voided_at?, voided_by?
room_events    seq, room_id, type, payload, created_at    -- СОЗДАНА, НО ПОКА НЕ ИСПОЛЬЗУЕТСЯ
```

Тонкости, которые легко сломать:

- **У `score_entries` два ключа.** `seq` — автоинкремент, задающий бесспорный порядок (нужен правилу «кто первым перешёл лимит»). `id` — uuid, который генерирует **клиент** ради идемпотентности: повтор запроса с тем же `id` не создаёт вторую запись.
- **Отмена не удаляет.** Счёт — это `SUM(points) WHERE voided_at IS NULL`, отменённая запись остаётся видна в раздачах.
- **Порядок участников — `ORDER BY joined_at, user_id`.** Разрешение `Date.now()` — миллисекунда; без второго ключа вошедшие одновременно меняли бы места за столом между играми.
- **Победитель пересчитывается по всему журналу** в той же транзакции, что и изменение журнала. Иначе два почти одновременных запроса объявят двух победителей. Отмена победной записи возвращает игру в `active`.

## API

Комната адресуется **кодом** (6 символов, алфавит без `O/0` и `I/1`), а не uuid: ссылка-приглашение и API говорят на одном языке. Регистр не важен.

```
POST /api/auth/guest        {nickname}          → {token, user}
POST /api/auth/upgrade      {email, password}   → привязать email к гостю
POST /api/auth/login        {email, password}   → {token, user}
GET  /api/me                                    → {id, nickname, hasEmail, activeRoomCode}

GET  /api/rooms                                 → RoomSummary[] (лобби)
POST /api/rooms             {name, password?}   → RoomState
GET  /api/rooms/:code                           → RoomSummary (любому: «нужен ли пароль»)
GET  /api/rooms/:code/state                     → RoomState (только участнику)
POST /api/rooms/:code/join  {password?}         → RoomState
POST /api/rooms/:code/leave                     → RoomState
POST /api/rooms/:code/games {scoreLimit}        → RoomState (старт и рестарт)

POST /api/games/:id/entries {id, userId, points} → RoomState
POST /api/entries/:id/void                       → RoomState
GET  /api/games/:id                              → плоская форма, оставлена для истории
```

**Единственная форма ответа** у всего, что меняет состояние:

```ts
type RoomState = {
  room:    { id, code, name, hasPassword, hostUserId }
  members: PublicUser[]                       // текущие участники комнаты
  game:    GameDetails | null                 // ПОСЛЕДНЯЯ игра в любом статусе
}
type GameDetails = {
  id, scoreLimit, status, startedAt, finishedAt, winnerUserId,
  players: PublicUser[]                       // состав, зафиксированный на старте
  entries: ScoreEntry[]                       // журнал, включая отменённые
  scores:  Record<userId, number>
}
```

Игра в состоянии — **последняя, а не активная**: иначе экран победы исчезал бы при обновлении страницы.

Сессия — случайный токен (32 байта) в `localStorage`, в базе только его SHA-256, заголовок `Authorization: Bearer`. Cookie не используются: домен один.

Ошибки везде `{error: string, message?: string}`. Внутренние сбои деталей не отдают. Ограничение попыток входа — 10 за 5 минут по паре «IP + комната».

Восстановление после F5: токен → `GET /api/me` → `activeRoomCode` → `GET /api/rooms/:code/state`.

## Что сделано и что дальше

**План 1 (выполнен).** Монорепо pnpm, схема SQLite, доменная логика, аутентификация, комнаты, игры, запись и отмена очков, завершение по лимиту, ограничение попыток.

**План 1b (выполнен).** Появился после проверки API глазами клиента, которая нашла семь дыр: не отдавались ники, состав комнаты и хост, после перезагрузки страницы человека выбрасывало в лобби, ответы имели три разные формы, вход по ссылке требовал двух запросов, ошибки — двух форматов. Причина была в спеке: там сказано «клиент загружает полное состояние комнаты при входе», но эндпоинта для этого в списке API не было.

**План 2 — realtime (не написан).** Журнал `room_events` (таблица уже есть), SSE с догрузкой по `Last-Event-ID`, presence по открытым соединениям, автопередача хоста через 60 секунд, пометка брошенных игр как `abandoned`. `RoomState` становится снимком, который SSE отдаёт при подключении, а события — дельтами к нему.

Технические требования к SSE из спеки: heartbeat-комментарий раз в 25 секунд (иначе прокси рвут простаивающее соединение), заголовки `Cache-Control: no-cache` и `X-Accel-Buffering: no`.

**План 3 — клиент (не написан).** `vue-router`, Pinia, маршруты `/`, `/room/:code`, `/history`, `/history/:gameId`. Существующие компоненты переиспользуются: `GameScreen` остаётся табло, но берёт счёт из стора; `PlayerCard` получает «онлайн» и «это вы»; `VictoryScreen` — кнопку «Играть ещё»; `SetupScreen` распадается на форму создания комнаты и выбор лимита при старте. Лимит очков принадлежит игре, а не комнате.

**План 4 — история и выпуск (не написан).** Запросы истории и статистики (`/api/me/games`, `/api/me/stats`), PWA, `Dockerfile`, раздача статики тем же сервером, деплой в Coolify.

## Как здесь принято работать

Процесс: брейншторм → спека → план с полным кодом каждого шага → исполнение по TDD (падающий тест, потом реализация) → коммит на каждую задачу. Скиллы `superpowers:brainstorming`, `writing-plans`, `executing-plans`.

Правила, оплаченные ошибками этой сессии:

1. **`pnpm typecheck` перед каждым коммитом.** Vitest типы не проверяет: неаннотированный обработчик ошибок с `err: unknown` прошёл все тесты и уехал в коммит.
2. **Проверять на живом сервере, а не только через `inject`.** `app.inject()` иначе выставляет `Content-Length`, и дефект «`POST` без тела с `content-type: application/json` отвечает 400» на нём не воспроизводился.
3. **Убивать фоновые серверы намертво.** Осиротевший процесс держал порт 3000, новые запуски молча выходили по `EADDRINUSE`, а `curl` разговаривал со старым бинарником. Час ушёл на диагностику несуществующего бага. Запускать на разных портах, проверять `lsof -ti tcp:PORT`.
4. **Тестировать сборку экрана, а не только ручки.** 103 теста дёргали эндпоинты поодиночке и пропустили, что клиент физически не может нарисовать табло. `server/test/screens.test.ts` рисует экран ожидания и табло и падает, если в них просочился хоть один uuid.
5. **Не завязывать тесты на порядок, который API не гарантирует.** Порядок мест зависит от времени входа с точностью до миллисекунды.

Коммиты и общение — по-русски. Сообщение коммита объясняет причину, а не пересказывает диф.
