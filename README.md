# Счётчик очков

Общий счёт для настольных игр: каждый пишет очки со своего телефона, все за столом видят их сразу.

Одно приложение в одном контейнере: Fastify отдаёт API, поток событий и собранный клиент с одного порта. Внешних сервисов нет — ни базы, ни кэша, ни брокера.

- Развернуть на своём сервере из репозитория → [docs/DEPLOY.md](docs/DEPLOY.md)
- Отдать готовый комплект чужому серверу → [deploy/README.md](deploy/README.md)

## Стек

| Часть | Чем сделано |
|---|---|
| Сервер | Node 22, Fastify 5, TypeScript, сборка в один файл через tsup |
| База | SQLite через `better-sqlite3`, режим WAL |
| Клиент | Vue 3, Pinia, Vue Router, Vite, PWA c service worker'ом |
| Общие типы | пакет `@score/shared` — исходники, без сборки |
| Реальное время | SSE (Server-Sent Events), журнал событий в базе |
| Тесты | Vitest: 213 серверных, 51 клиентский |

Монорепозиторий на pnpm workspaces: `server/`, `client/`, `shared/`.

## База данных

**Подключена, внешнюю поднимать не нужно.** Это SQLite: один файл, который открывает сам процесс приложения.

- Путь задаётся `DB_PATH`, в образе это `/data/score.db`, а `/data` — том Docker. Без тома передеплой сотрёт историю.
- Схема применяется при старте: `openDb()` выполняет `SCHEMA_SQL` из `server/src/db/schema.ts`, весь DDL написан через `CREATE TABLE IF NOT EXISTS`. Отдельного шага миграции нет, запуск на пустом каталоге сразу рабочий.
- `journal_mode = WAL` — чтобы чтения не ждали записи; `foreign_keys = ON` — ссылочная целостность проверяется базой.
- Таблицы: `users`, `sessions`, `rooms`, `room_members`, `games`, `game_players`, `score_entries`, `room_events`.

Драйвер синхронный, и это осознанный выбор: транзакция `better-sqlite3` атомарна относительно цикла событий, поэтому порядок рассылки событий совпадает с порядком их `seq` без дополнительной синхронизации.

Про бэкап (`VACUUM INTO`, а не `cp`) и восстановление — в [docs/DEPLOY.md](docs/DEPLOY.md#бэкап).

## Как это работает

### Вход

Регистрации нет: `POST /api/auth/guest` с ником создаёт пользователя и сессию. Токен — 32 случайных байта; в базе лежит только его SHA-256, поэтому подписывать и хранить секреты не нужно. Клиент держит токен в `localStorage` и шлёт как `Authorization: Bearer`. Гость может позже привязать почту с паролем (`/api/auth/upgrade`, argon2) — тогда он войдёт с другого устройства.

### Комната

Комната — код из 6 символов алфавита без `O/0` и `I/1`: его диктуют голосом и вводят с телефона. Код в URL нечувствителен к регистру. У комнаты может быть пароль; подбор ограничен 10 попытками за 5 минут на пару «IP + комната», чтобы блокировка одной комнаты не закрывала вход в остальные.

### Поток событий

Обновления идут по SSE, а не поллингом или веб-сокетами: трафик односторонний, и по SSE его достаточно.

Подключение — в два шага. Браузерный `EventSource` не умеет отправлять заголовки, а токену сессии не место в URL: он осел бы в журналах прокси. Поэтому клиент берёт одноразовый билет (`POST /api/rooms/:code/events/ticket`, живёт 30 секунд, сгорает при предъявлении) и открывает поток с ним.

Кадры в потоке:

| Событие | Смысл |
|---|---|
| `sync` | полный снимок комнаты сразу после подключения |
| `missed` | события, пропущенные за время обрыва, по `Last-Event-ID` |
| `presence` | кто сейчас на связи; без `id`, потому что в журнал не пишется |
| `member_joined`, `member_left`, `host_changed`, `game_started`, `game_finished`, `entry_added`, `entry_voided` | запись журнала + итоговый снимок |

Состояние всегда приезжает снимком целиком — клиент его заменяет, а не собирает из дельт. `payload` нужен только для уведомлений вида «Петя отменил запись». Поэтому расхождение состояний невозможно в принципе: сходиться нечему.

Все изменения проходят через одну обёртку `mutateRoom`: мутация и запись в журнал идут одной транзакцией, рассылка — строго после коммита. Откат физически не может оставить разосланное событие, а автор запроса получает в ответе тот же снимок, что ушёл в поток.

Живучесть соединения: сервер шлёт `ping` раз в 25 секунд (именованным событием, а не комментарием — иначе клиент не отличит живой поток от полуоткрытого), отдаёт `X-Accel-Buffering: no` и `Cache-Control: no-transform`. Клиент переподключается сам, с задержками 0.5 → 10 секунд, каждый раз за новым билетом, и держит `Last-Event-ID` в своей памяти.

**Сжимать `text/event-stream` нельзя** — буфер компрессора копит кадры, и обновления приходят пачками. В конфигах прокси из репозитория это учтено; при своём прокси проверьте.

### Правила партии

- Начать игру может только хост, состав фиксируется на старте: 2–10 игроков.
- Свои очки пишет каждый сам, чужие — только хост. Ушедший из состава не пишет никому.
- Победа считается **проигрыванием всего журнала** по порядку `seq`: первый, кто накопил лимит, и есть победитель. Отменённые записи пропускаются, поэтому отмена задним числом корректно меняет исход — а если победной записи больше нет, партия возвращается в активные.
- Записи не удаляются, а гасятся: отменённые остаются видны в журнале, чтобы за столом не спорить, кто что исправил.
- Исправление очков — отдельный маршрут `/entries/:id/replace`, одной транзакцией. Двумя запросами отмена победной записи успевала вернуть игру в активные, и экран победы мигал у всех за столом.
- Записи идемпотентны по идентификатору от клиента: повтор запроса после обрыва не создаёт вторую строку и не порождает лишнего события.
- Хост пропал — роль через минуту уходит следующему участнику по порядку мест, а не случайному. Вернулся раньше — остаётся хостом.
- Сутки без единой записи — партия помечается брошенной и в статистику не идёт.

### Один процесс

Presence и билеты живут в памяти процесса: после рестарта клиент возьмёт новый билет, а онлайн соберётся заново из переподключений. В базу они не пишутся намеренно — это состояние соединений, а не данных.

## API

Всё под `/api`, ответ на любую неудачу — единой формы `{ error, message? }`. Авторизация везде, кроме `/auth/guest`, `/auth/login` и самого потока (там билет).

| Метод | Путь | Что делает |
|---|---|---|
| `POST` | `/auth/guest` | вход по одному нику, возвращает токен |
| `POST` | `/auth/login` | вход по почте и паролю |
| `POST` | `/auth/upgrade` | привязать почту и пароль к текущему гостю |
| `GET` | `/me` | кто я + код комнаты, куда вернуться |
| `POST` | `/rooms` | создать комнату |
| `GET` | `/rooms` | список открытых комнат |
| `GET` | `/rooms/:code` | краткая сводка по коду |
| `GET` | `/rooms/:code/state` | полный снимок комнаты |
| `POST` | `/rooms/:code/join` | войти, при необходимости с паролем |
| `POST` | `/rooms/:code/leave` | выйти |
| `POST` | `/rooms/:code/events/ticket` | билет на поток |
| `GET` | `/rooms/:code/events` | сам поток (SSE) |
| `POST` | `/rooms/:code/games` | начать партию с лимитом очков |
| `GET` | `/games/:id` | разбор партии: состав, журнал, счёт |
| `POST` | `/games/:id/entries` | записать очки |
| `POST` | `/entries/:id/void` | отменить запись |
| `POST` | `/entries/:id/replace` | исправить очки одной транзакцией |
| `GET` | `/me/games` | мои партии (`limit`, по умолчанию 50) |
| `GET` | `/me/stats` | сводка: партии, победы, лучший счёт, соперники |
| `GET` | `/health` | `{"status":"ok"}`, используется в healthcheck |

Ненайденный `GET` вне `/api` отдаёт `index.html` — иначе прямая ссылка `/room/КОД`, единственный способ позвать друга, возвращала бы 404. Запросы к `/api` так не обрабатываются: опечатка в адресе вернула бы HTML, и клиент упал бы на разборе.

## Переменные окружения

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `PORT` | `3000` | порт HTTP |
| `DB_PATH` | `./score.db` (в образе `/data/score.db`) | файл SQLite |

Переменные развёртывания (`DOMAIN`, `PROXY_NETWORK`, `TRAEFIK_ENTRYPOINT`, `HOST_PORT`, `TAG`) — в [`.env.example`](.env.example), приложение о них не знает.

## Развёртывание

Приложение слушает 3000 и о TLS ничего не знает: наружу его выставляет обратный прокси. Два готовых пути.

**Готовый образ, свой домен и HTTPS одной командой.** Комплект из `deploy/`: образ тянется из `ghcr.io`, Caddy сам получает сертификат Let's Encrypt.

```bash
# на сервер уходят три файла из deploy/: compose.yaml, Caddyfile, .env.example
cd /srv/score && cp .env.example .env && nano .env   # вписать DOMAIN
docker compose up -d
```

**Из репозитория, если прокси на машине уже есть.** Базовый `compose.yaml` наружу не смотрит вообще, направление трафика выбирается накладкой:

```bash
docker compose -f compose.yaml -f compose.traefik.yaml up -d --build   # есть Traefik (в т.ч. от Coolify)
docker compose -f compose.yaml -f compose.port.yaml    up -d --build   # впереди nginx или Caddy на хосте
```

Подробности, примеры конфигов nginx/Caddy, проверки после выкатки и бэкап — [docs/DEPLOY.md](docs/DEPLOY.md).

Обновление в обоих случаях — `docker compose pull && docker compose up -d`. Данные не трогаются, игроков не выбивает: сервер ловит `SIGTERM`, закрывает потоки и снимает таймеры, а клиенты переподключаются сами и догружают пропущенное.

## Образ

Собирается в GitHub Actions, а не на ноутбуке: у разработчика arm64, а сервера обычно amd64 — локально собранный образ там просто не запустится. Каждый push в `main` публикует `ghcr.io/raul-cortez/score-counter` под тегами `latest` и `sha-<полный sha>` (второй — чтобы было куда откатиться) для `linux/amd64` и `linux/arm64`.

Dockerfile мультистейджный: зависимости отдельным слоем ради кеша, сервер собирается в один файл, нативные модули (`better-sqlite3`, `@node-rs/argon2`) остаются внешними и приносятся из слоя зависимостей. Работает под пользователем `node`, healthcheck ходит на `/api/health`.

## Разработка

Нужны Node 22 (`.nvmrc`) и pnpm 9 через corepack.

```bash
corepack enable
pnpm install

pnpm dev:server      # tsx watch, порт 3000, база ./score.db
pnpm dev:client      # Vite, порт 5173, /api проксируется на 3000
```

В разработке это два процесса: `STATIC_ROOT` не задана, поэтому сервер отдаёт только API. В проде их раздаёт один Fastify — одного домена достаточно, значит нет CORS.

```bash
pnpm test            # серверные тесты
pnpm --filter client test
pnpm typecheck       # по всем пакетам
pnpm build           # shared → server → client
```

Тесты идут на настоящей SQLite в памяти и настоящем Fastify, без моков; поток проверяется живым клиентом SSE.

## Границы

Известные ограничения — следствия выбранной простоты, а не недоделки:

- **Один экземпляр.** Файл SQLite, реестр соединений и билеты в памяти процесса — горизонтально это не масштабируется. Для стола на десять человек и не нужно.
- **Нет миграций.** Схема доводится `IF NOT EXISTS`; несовместимое изменение потребует писать миграцию руками.
- **Почта не подтверждается.** Проверка адреса намеренно минимальная: строгие регулярные выражения отвергают действительные адреса чаще, чем ловят опечатки.
- **Ограничение частоты только на вход в комнату.** У `/auth/login` его нет.
- **Комнаты не закрываются сами.** Поле `closed_at` в схеме есть, маршрута нет.
